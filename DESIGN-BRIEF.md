# Design Brief: GitHub Push Event Ingestion Service

## Problem Understanding

The prompt asks for an internal service that ingests GitHub Push events, enriches them with related data, and stores them for querying and analysis. Reading between the lines, the core challenge isn't the ingestion itself—it's doing it responsibly under tight constraints: no auth token (60 req/hr), the need to run unattended without crash-looping, and making the data actually useful for future consumers.

I interpreted this as: build a polling pipeline that continuously pulls from the GitHub Public Events API, filters for `PushEvent` types, enriches them with actor/repository metadata, and persists everything durably in PostgreSQL. The system should be boring in production—predictable, observable, and graceful under failure.

## Proposed Architecture

**Runtime:** Java 25, Spring Boot 4, PostgreSQL, Docker Compose  
**Why not Rails:** Java/Spring Boot is my strongest stack. The architecture and design thinking are the same regardless of framework—the language is incidental to the system design.

### Components

The application follows a standard Spring Boot layered architecture:

- **Web (Controllers)** — REST endpoints for querying persisted events. Handles request binding and response serialization.
- **Service** — Business logic layer. The ingestion service orchestrates polling, filtering, deduplication, and persistence. The query service translates API parameters into repository calls via JPA Specifications.
- **Repository (JPA)** — Data access layer. Spring Data JPA repositories handle persistence and provide derived query methods and specification-based lookups for structured field filtering.

### Data Model

Three tables managed by Liquibase, each with a database-generated UUIDv7 primary key (via PostgreSQL 17's `uuidv7()` function):

**`actors` table:**
| Column | Type | Notes |
|--------|------|-------|
| id | UUID (PK) | Generated by DB via `uuidv7()` |
| actor_id | BIGINT (unique) | GitHub actor ID, dedupe key |
| url | VARCHAR | Actor API URL |
| login | VARCHAR | GitHub username |
| avatar_url | VARCHAR | Profile image URL |
| gravatar_id | VARCHAR | Gravatar identifier |
| display_login | VARCHAR | Display format of username |

**`repositories` table:**
| Column | Type | Notes |
|--------|------|-------|
| id | UUID (PK) | Generated by DB via `uuidv7()` |
| repository_id | BIGINT (unique) | GitHub repo ID, dedupe key |
| url | VARCHAR | Repository API URL |
| name | VARCHAR | Full repo name (owner/repo) |

**`push_events` table:**
| Column | Type | Notes |
|--------|------|-------|
| id | UUID (PK) | Generated by DB via `uuidv7()` |
| event_id | VARCHAR (unique) | GitHub event ID, dedupe key |
| actor_id | BIGINT | GitHub actor ID from event payload |
| repository_id | BIGINT | GitHub repo ID from event payload |
| push_id | BIGINT | From `payload.push_id` |
| ref | VARCHAR | From `payload.ref` |
| head | VARCHAR(40) | From `payload.head` |
| before | VARCHAR(40) | From `payload.before` |
| raw_payload | JSONB | Full event JSON for audit |

**No foreign key constraints** are enforced at the database level. The relationships between `push_events.actor_id` → `actors.actor_id` and `push_events.repository_id` → `repositories.repository_id` are maintained at the application level. The poller guarantees actor and repository records exist before inserting the push event. This avoids write-ordering complexity and keeps inserts simple—particularly important since the tables use natural GitHub IDs rather than internal UUIDs for the relationship.

### Enrichment Approach

Actor and repository data is extracted directly from the event payload rather than fetched from secondary API endpoints. Each event already contains `actor.id`, `actor.login`, `actor.avatar_url`, `repo.id`, `repo.name`, etc. This avoids additional API calls entirely, which is critical given the strict 60 req/hr unauthenticated rate limit.

The `existsByActorId` / `existsByRepositoryId` checks provide insert-if-not-exists semantics—actor and repo records are written once on first encounter and not updated on subsequent events. This keeps ingestion fast and avoids amplifying API usage.

### Polling Strategy

A `@Scheduled(fixedDelay = 60, timeUnit = SECONDS)` poller runs continuously from application startup:

1. Fetches all public events from the configured GitHub Events API URL.
2. Iterates over raw JSON nodes, deserializes each into a typed DTO for structured field access.
3. Filters for `PushEvent` type only; all other event types are discarded.
4. Checks `existsByEventId` to skip already-ingested events (fast path).
5. Persists actor and repository if not already known.
6. Persists the push event with structured fields extracted from the DTO and the raw JSON node preserved as the `raw_payload`.

**Future enhancement: ETag-aware polling.** The GitHub Events API supports conditional requests via `ETag` / `If-None-Match` headers, returning `304 Not Modified` when no new events exist (without consuming rate limit). The API also returns an `X-Poll-Interval` header indicating the minimum poll interval. Implementing this would reduce wasted requests to near-zero during quiet periods. See `EXTENSION-DESIGN.md` (Extension A) for the full design.

### Durability & Idempotency

- Events are deduplicated by `event_id` (unique constraint). If the poller restarts or re-fetches overlapping data, duplicates are silently rejected.
- A `DataIntegrityViolationException` catch handles the race condition where an event is inserted between the exists-check and the save.
- The `fixedDelay` scheduler guarantees no overlapping poll executions.
- Liquibase manages schema migrations, ensuring repeatable and versioned DDL changes.
- `spring.jpa.hibernate.ddl-auto=validate` ensures the application refuses to start if the schema doesn't match the entity model.

### Observability

Structured logging (SLF4J + Logback) to stdout/stderr for Docker log aggregation:

- `INFO` — "Polling GitHub Events API" at cycle start; "Poll complete: ingested=X, skipped(duplicate)=Y" at cycle end
- `WARN` — Empty API response
- `ERROR` — HTTP fetch failures, JSON parse failures, individual event deserialization failures (with context)

Malformed events are logged and skipped rather than crashing the ingestion loop. A failure on one event does not affect processing of subsequent events in the same batch.

### Query Layer

A single REST endpoint `GET /events` accepts optional query parameters (`actorId`, `repositoryId`, `pushId`, `ref`, `head`, `before`) bound to a `SearchPushEventRequest` record. The service builds a JPA Specification by composing per-field predicates with AND semantics. Null parameters are ignored (no predicate added), so any combination of filters works.

Swagger UI is available at `/swagger-ui/index.html` via springdoc-openapi.

## Key Tradeoffs and Assumptions

| Decision                           | Tradeoff                                                                                                                                    |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| JSONB raw payload retained         | Storage cost for full audit trail; enables reprocessing if schema evolves                                                                   |
| Enrichment from event payload only | No additional API calls; data is limited to what the event contains (no full profile details), but avoids rate limit amplification entirely |
| No foreign keys                    | Simpler writes with no ordering constraints; referential integrity maintained by application logic                                          |
| UUIDv7 generated by database       | Time-ordered PKs without application-side generation; requires PostgreSQL 17+                                                               |
| Single-threaded poller             | Simpler correctness; sufficient for 60s cadence against one endpoint                                                                        |
| No ETag/conditional requests (yet) | Simpler initial implementation; every poll costs a request even when unchanged. Documented as future enhancement                            |
| No authentication token            | Limited to 60 req/hr; viable for the public events endpoint's low-frequency polling                                                         |
| Liquibase for migrations           | Explicit versioned DDL; supports rollback and is already in the Spring Boot ecosystem                                                       |
| Client-side type filtering         | GitHub public events endpoint does not support server-side type filtering; we discard non-PushEvent in the service layer                    |

**Assumptions:**

- The GitHub timeline returns at most 300 events. In practice, with 60s polling, the default page size captures the recent window without needing pagination.
- Unauthenticated rate limit of 60 req/hr is sufficient for single-page polling at 60s intervals (60 req/hr exactly matches our budget).
- Events older than 30 days are not available from the API—we accept this as a data boundary.
- PostgreSQL 17+ is used (`postgres:latest`), providing native `uuidv7()` support.

## What I Intentionally Did Not Build

- **ETag-aware polling** — Designed in `EXTENSION-DESIGN.md` (Extension A). Would reduce rate limit consumption to near-zero during quiet periods. Deferred to keep the initial implementation simple.
- **Webhook ingestion** — Would eliminate polling overhead but requires public endpoint exposure and GitHub App configuration; out of scope for a local Docker system.
- **Message queue / async workers** — The volume from a single unauthenticated endpoint doesn't justify the complexity of Kafka/RabbitMQ. A scheduled thread suffices.
- **Object storage for avatars** — Designed in `EXTENSION-DESIGN.md` (Extension C). Would add S3/MinIO and a download-once pipeline. Deferred.
- **Retention policy** — Designed in `EXTENSION-DESIGN.md` (Extension B). Would prevent unbounded table growth via scheduled cleanup. Deferred for short-lived evaluation environments.
- **Full-text search** — Queryable structured columns with JPA Specifications satisfy the stated requirements. Elasticsearch would be overkill at this scale.
- **Secondary enrichment fetches** — Could call `actor.url` and `repo.url` for richer data, but the 60 req/hr limit makes this impractical without authentication. The event payload provides sufficient data.
- **Authentication** — The prompt explicitly states no token. If added later, rate limits increase to 5000 req/hr, enabling pagination, richer enrichment, and ETag becomes less critical.
- **Horizontal scaling** — Single instance is correct for this workload. Distributed locking (e.g., ShedLock) would be needed if scaled out.
